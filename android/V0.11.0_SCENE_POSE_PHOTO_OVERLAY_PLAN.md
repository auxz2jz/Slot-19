# Android v0.11.0 — honest full-frame coverage, shared scene pose, photo overlays

## User instruction
User asked: “Yes do that I thought the program was analyzing all the photos and making a point cloud out of several hundred photos.” This follows screenshot/ZIP evidence v0.10 (same imported 300-frame video) demonstrating first two-view scene 158 3D points and ROI-first **LOW_PARALLAX 0.3039°** with zero accepted ROI points, so multi-view button disabled. User separately wanted semi-transparent original photo over the point cloud to see which source image pixels contributed 3D points.

## Clarify workflow
Frame extraction saved **300 original JPEG images** and ORB geometry examined 75 sampled adjacent pairs. Sparse scene 3D picked ONE initial two-photo pair from a bounded list; v0.10 multi-view then attempted at most **8 additional** images IF ROI-first baseline passed. It never built 3D from all 300. v0.11 increases opt-in per-source anchor multi-view attempts to **every saved photo other than both first pair frames, up to max 300**; this is CPU heavy and can take several minutes. Crucially it still uses first-photo anchor descriptor tracking, NOT a full 300-view global SfM with sequential keyframe track chaining, calibration and bundle adjustment. Not every photo can be registered or contributes points; reports distinguish attempted/registered/contributing and NEW XYZ counts. No fake dense model.

## Early ROI low parallax fix
Existing reliable full scene camera pose recovered from broad scene features on the SAME selected pair is recorded in `sparse_report.json.selectedPair.cameraPoseRotationRowMajor` and `cameraPoseTranslation` only for accepted baseline. If early ROI selected exact SAME source pair (e.g. both [0,6]), v0.11 ORB detects only inside the manually marked rectangles and **triangulates the ROI descriptor matches using the full-scene camera rotation and translation**, instead of estimating a degenerate second camera pose from a small target with repetitive texture. 3D points are subjected to positive-depth, 0.8–30° parallax and reprojection gates; if insufficient credible points report INCONCLUSIVE, never force-enable nonexistent model. ROI-first 3D in that path is in SAME arbitrary scene-relative coordinate frame; otherwise legacy independent ROI pose is used and marked with a warning. The multi-view baseline uses the same scene-pose support when applicable. The checkerboard calibration remains unapplied due image aspect/crop mismatch. This correction targets v0.10 ROI pair 0.3039° vs accepted scene 9.8485° disparity, without relaxing parallax thresholds.

## New photo-point overlay
**Overlay 3D Points on Original Photos** button appears once original sparse scene exists, even if early ROI cloud FAILED. Full-height source photo canvas shows green circles at **exact normalized original matched 2D feature pixels that correspond to already triangulated XYZ points** on two saved source photos. Choose Full Scene, filtered-scene subset, or ROI-first model (only when separately generated); switch Photo 1 / Photo 2; sliders control original PHOTO alpha 0–100% and dot radius. All source 2D coordinates are stored 1:1 in original scene `sparse_point_projections.json`, and new `early_object_point_projections.json`, with original PLY SHA256 fingerprint, run ID and source frame pair, no guessing. Legacy scene filter `object_focus_report.json` now saves exact `sourcePointIndices` to match filtered PLY to original keypoint rows; backwards-compatible fallback reconstructs indices from saved ROI boxes. Missing/hash-inconsistent mapping means transparent error, not made-up alignment. This **shows measured keypoint positions**, NOT arbitrary camera projection for unrelated photos. Multi-view overlay is purposely omitted until each extra view's camera matrices & observed feature tracks are persisted; avoid false visual precision.
No video frames are included in diagnostic ZIPs; point overlay uses original source JPG stored app-private, not export.
