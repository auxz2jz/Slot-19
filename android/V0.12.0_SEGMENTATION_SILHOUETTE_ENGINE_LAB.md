## Three-stage, multi-engine Android prototype
1. **Foreground-mask engine competition:** After choosing real object in source Photo 1/Photo 2, choose one of 4 `MaskEnginePolicy` strategies: `BOX_BASELINE` (explicit full rectangle), OpenCV **GrabCut** color segmentation, **LOW_TEXTURE** local image-Laplacian gradient heuristic (specifically probes flat object versus busy checkerboard), and **CONSENSUS_INTERSECTION** of GrabCut+low-texture. These independently produce normalized PNG pixel masks at <=800px max axis and one `foreground_mask_report.json` with per-image area fraction, which methods passed coverage gates and mask Jaccard/IoU disagreement. Only real candidate masks; they are NOT guaranteed object segmentation and can get fooled by checkerboard, especially white/black smooth patches. Source photo images are not included in redacted ZIPs.
2. **Mask-constrained object features:** The selected engine's active masks are tied to a SHA256 of the exact user's two ROI selections. When available and both pass validity checks, early ROI-first and multi-view ORB `features()` use the true foreground pixel mask INTERSECTED with the user ROI, BEFORE feature extraction, while the whole-scene features still position the camera. Re-run Analyze Sparse 3D after running the mask engine; watch differences in 3D points, not only raw counts. No fallback to stale masks from a changed selection. If engine fails, original rectangle-only matching remains for recovery, with report `segmentationUsed=false`.
3. **Silhouette voxel hull + geometric mask/sparse fusion:** During the existing multi-view PnP pass, successful registered extra views now persist rotation/translation, working camera intrinsics and frame number (not just counts). After Multi-View succeeds with shared scene/ROI local coordinates, **Test Silhouette Visual Hull + Mask Fusion** reads the user's original 2 source masks, projects ROI-first sparse points into up to 10 additional PnP-registered camera views to approximate object bounding boxes (camera-guided ROI tracking), and independently performs foreground segmentation in those source photographs. When >=3 masks from distinct registered camera views are valid, a **28×28×28 bounded 3D voxel grid** in relative local XYZ gets carved by projected silhouette consistency. Separately, a conservative `mask_verified_sparse.ply` filters the *full registered multi-view PLY* by agreement with all those masks, avoiding unaligned camera-coordinate merges. Outputs `silhouette_voxel_hull.ply`, `mask_verified_sparse.ply`, and `silhouette_hull_report.json` show mask views, voxels, XYZ input/survivors and per-extra frame status. No fake PLY if fewer than 3 silhouette views or no occupancy. Voxel bounds are inferred from sparse ROI XYZ, so may be WRONG if current sparse cloud is mostly checkerboard; camera-guided ROI tracking is a heuristic, **not proven correct object tracking across hundreds of frames**.
4. **Visualization:** `Overlay 3D Points on Original Photos` gains transparent ORANGE segmentation-mask layers with engine picker; existing green dots retain genuine source feature-to-XYZ relationship. User should visually verify that ORANGE mask covers OBJECT, NOT CHECKERBOARD before trusting silhouettes/3D.
5. **Isolation/diagnostics:** Existing 4 clouds unchanged. New silhouette and mask/sparse PLY names are unique/versioned and have native 3D viewer/export. Mask report/hull report/error included in latest and ALL-run ZIPs, never raw source PNGs/photos. All actions, result/inconclusive/errors logged. Keep original XYZ, ROI, filtered and multi-view independently recoverable.
6. **Safety/interpretation:** No metric calibration or distortion handling solved. A silhouette voxel candidate is NOT a clean watertight STL mesh, does not reveal concavities, hidden surfaces or true physical scale. Alternative masks and low-texture heuristics may be completely wrong for uniformly colored checkerboards. Do not interpret fusion count increase/decrease as better shape without user visually confirming segmentation.

## Other engines to test later, WITHOUT pretending they are installed on this phone
- **COLMAP** (open-source PC/server SfM + multi-view stereo) — strongest first independent baseline for full-sequence camera registration, feature tracks, camera bundle adjustment and potential dense point cloud; can use Android exported camera JPEGs once explicit user export action is implemented. [Official](https://colmap.github.io/).
- **openMVG + OpenMVS** (open-source PC/SfM plus MVS densification and meshing) — independent geometry check against COLMAP. Need interoperable camera poses and consistent scale before combining outputs. [Docs](https://openmvg.readthedocs.io/en/latest/software/SfM/SfM/).
- **AliceVision / Meshroom** (PC photogrammetry workflow) — different feature extraction, camera solving and dense reconstruction. [GitHub](https://github.com/alicevision/meshroom).
- **Learned segmentation** (MobileSAM / SAM model variants via ONNX/TFLite) — promising for checkerboard separation but *not included* in v0.12; Android model compatibility, offline size, licensing, memory, and battery must be independently tested before downloading/bundling. Neural masks cannot substitute for valid 3D poses.
- **Traditional OpenCV foreground alternatives**: Watershed, K-means/Lab color distance, background frame subtraction if an empty scene can be captured. Background subtraction could separate stationary object only if an object-free reference from same locked camera pose exists; handheld changing camera invalidates naive subtraction. Mask alternatives should be evaluated against hand-labeled object outlines on actual source photos, not defaulted by raw point count.

## Multi-engine workflow / fusion contract
- Run engines INDEPENDENTLY first and save mask comparison statistics, no silent autowinner.
- User chooses preferred mask based on orange overlay, not whether checkerboard gave more 3D dots.
- Background ORB remains a camera-position reference; foreground/mask ORB contributes object XYZ; PnP extra camera poses come from registered feature tracks.
- Fuse only when **same source run + verified common camera coordinate frame + mask selection identity + pose quality gates + sufficient photo coverage**. Never concatenate PLYs from independent arbitrary origins or scale; never overwrite another algorithm's output.
- If masks disagree or silhouette tracking fails, report INCONCLUSIVE and preserve each independent point cloud and the raw diagnostic counts.
- Tests include MaskEnginePolicy and SilhouettePolicy, existing cloud/export non-collision and source/reprojection policies. CI cannot prove segmentation visually; user must test on phone.

## Device test, in actual sequence
1. Install new side-by-side 0.12 Preview (don't remove 0.11). Import your same 300-frame video again.
2. Select object BEFORE Sparse 3D in actual Photo1/Photo2 with one-finger boxes. Compare each mask engine in **Compare Foreground Mask Engines**, initially try `GRABCUT` then `LOW_TEXTURE` then `CONSENSUS_INTERSECTION`. In Photo Overlay view green dots and ORANGE mask for both source photos; note specifically whether checkerboard pixels are orange or the object body is orange. If mask is poor, do NOT trust generated silhouette as accurate.
3. With a chosen acceptable mask, tap Analyze Sparse 3D, then optional full 298-extra-view Multi-View (may take several minutes). Compare independent scene / ROI / filtered / multi-view PLY and image matches.
4. If a valid, scene-aligned Multi-View PLY exists, tap **Test Silhouette Visual Hull + Mask Fusion**. Watch whether >=3 tracked mask views survive, inspect voxel and mask-sparse PLYs and clearly labeled counts. Inconclusive is expected for poor/repetitive features.
5. Export latest+ALL ZIP and all six PLY variants that exist (no PLY when inconclusive), send both photos/mask screenshot if willing and report whether the object outline, as distinct from checkerboard, is visible.
6. Test older calibration-first problem and accidental landscape rotation separately; no claim that those are fully solved.
